- **`backup-offsite.sh` could not encrypt to a normal `[SC]`-primary / `[E]`-subkey GPG key — `--recipient "${FP}!"` forced the unusable primary key** (`agent/backup-offsite.sh`) — The #729 hardening pinned the recipient to the verified 40-char primary fingerprint, which is correct, but appended a trailing `!` to force "exactly this key." For the standard GnuPG layout — a sign/certify-only primary key with encryption delegated to a separate `[E]` subkey — the `!` forces the *primary*, which has no encryption capability, so `gpg --encrypt` aborts with `skipped: Unusable public key` / `encryption failed: Unusable public key` and exits 2. Fix: drop the `!`. The bare primary fingerprint still resolves to exactly that one key (a rogue key imported under the same email has a different primary fp and is already rejected by the preflight fingerprint check), and gpg then auto-selects that key's valid encryption subkey — preserving the #729 anti-substitution guarantee while actually being able to encrypt. Verified live: with the fix, `backup-offsite.sh` encrypted `marvin-backup-20260527-010001.tar.gz` (4.4 MB) to subkey `449635A16CB04080` and uploaded the ciphertext to `dev.infowebsro.cz:/incoming/` (4,587,715 bytes, confirmed via remote `ls -l`) — the first successful off-site backup, closing the operational gap behind #435/#716. `bash -n` + `shellcheck -S error` clean.

The previous handler `sed -n '2,53p' "$0"` (the most-recent expansion under #730) is robust today but drifts the instant any line is inserted or removed in the header block. - **`backup-offsite.sh` cleans up `CIPHER_FILE` if a failure fires between encrypt success and the SFTP batch trap** (`agent/backup-offsite.sh`) — fixes #732. The base `trap marvin_error_trap ERR` that was restored after a successful `gpg` did not include `rm -f "$CIPHER_FILE"`, so a failure on `chmod 600`, `stat`, `mktemp`, or the control-character rejection loop's `exit 1` would leave the encrypted backup on disk indefinitely — no confidentiality breach (it's encrypted to a key whose private half is not on the VPS), but repeated failures would accumulate `.gpg` files that nothing reaps. Two changes: (a) the trap restored after `gpg` now includes `rm -f "$CIPHER_FILE"` so the ERR path on `chmod`/`stat`/`mktemp` cleans up; (b) the rejection loop's `exit 1` (which bash does **not** route through the ERR trap) gets an explicit `rm -f "$CIPHER_FILE"` immediately before exiting. The wider trap on the SFTP batch block (line 228) already covered `CIPHER_FILE`, and the post-SFTP path is unchanged — `sftp_exit -ne 0` still preserves the ciphertext for retry (#719), and the explicit `rm -f "$CIPHER_FILE"` on the success path still runs. `bash -n` + `shellcheck -S error` clean.

- **`backup-offsite.sh --file` now rejects already-encrypted `.gpg` ciphertexts** (`agent/backup-offsite.sh`) — fixes #733. - **`weekly-enhance.sh` Phase 1 silently dies on first PASS — `((VAR++))` returns exit 1 under `set -e` when VAR is 0** (`agent/weekly-enhance.sh`) — A latent bug since the script was written: `((TEST_PASS++))` and `((TEST_FAIL++))` (21 instances total in Phase 1 self-tests) use the **post-increment** form, which evaluates to the value *before* the increment. When `TEST_PASS=0` and `((TEST_PASS++))` is the next statement, the expression evaluates to `0`, which arithmetic context treats as "false" → exit code 1 → `set -euo pipefail` kills the script. The first iteration of the very first self-test loop (line 35, `for script in agent/*.sh`) always tripped this — the script logged `--- Phase 1: Self-Tests ---` and died before Phase 1b (Codebase Health Score) ever ran. Confirmed by the empty `/var/log/marvin-weekly.log` (0 bytes since 2026-05-18 logrotate creation) and by the missing "Codebase health" log lines in `data/logs/2026-05-17.log` between the `Phase 1: Self-Tests` entry at 08:00:01Z and the next cron job at 08:02:01Z. Side effect: `data/codebase/health.json` (regenerated only by `weekly-enhance.sh`) has been **stale since 2026-05-16T08:11Z** — 6 days — reporting `error_trap_coverage_pct: 66` even though yesterday's PR #708 brought it to 100%. Why no ERR trap output in the 2026-05-17 log: on that date `weekly-enhance.sh` did not yet have `trap marvin_error_trap ERR` — PR #708 (2026-05-20) added it. So the script died silently. Next Sunday it would have died loudly but still died. **Fix**: replaced all 21 occurrences with the pre-increment form `((++VAR))`, which evaluates to the value *after* the increment — always non-zero — so `set -e` never trips. Minimal diff (single character change per line), no semantic difference in the counts. Verified three ways: (1) `bash -n` + `shellcheck -S error` clean on `weekly-enhance.sh`; (2) synthetic Phase 1 self-test loop (37 scripts, set -euo pipefail + trap) runs end-to-end and reports `PASS=37 FAIL=0 exit=0` instead of dying on the first `((++TEST_PASS))`; (3) post-fix manual run of `codebase-health.sh` regenerates `data/codebase/health.json` with `error_trap_coverage_pct: 100`, score 92→97, grade A — confirming the metric is now wired up to reach disk again. Also codifies a previously-undocumented bash gotcha: `((VAR++))` is one of the few `(( ... ))` forms whose exit code can be 1 even though the expression "succeeded" — prefer `((++VAR))` or `((VAR+=1))` for counters under `set -e`. **Next time** anyone audits the codebase for similar bugs: `grep -rn '((.*++))' agent/` returned only the 21 instances in this file, so this fix closes the gap completely; `((.*--))` returned zero matches.

- **`backup-offsite.sh` `--file` without PATH now errors instead of silently falling back to latest backup** (`agent/backup-offsite.sh`) — Addresses #731. - **`backup-offsite.sh` SFTP heredoc injection via control characters in `BACKUP_OFFSITE_REMOTE_DIR`** (`agent/backup-offsite.sh`) — Addresses #724. The SFTP batch file is built with a heredoc that interpolates `${REMOTE_DIR}`, `${CIPHER_FILE}`, and `${REMOTE_NAME}` directly. A newline in any of those values would smuggle an extra SFTP command onto its own line; the client would execute the lot under `marvin-backup`'s permissions on the remote. `REMOTE_DIR` is operator-controlled (env var); `REMOTE_NAME`/`CIPHER_FILE` derive from `SOURCE`, which can come from the `--file` argument, so defense-in-depth applies there too. **Fix**: a preflight loop right before the heredoc that rejects any value containing a control character (`*[[:cntrl:]]*` — newline, CR, tab, NUL, etc.) and exits 1 with `marvin_log "ERROR"` naming the offending variable. Placed at the point of use rather than at the top of preflight, so the safety check sits beside the vulnerable string-builder and won't drift apart from it during future refactors. The script doesn't trigger today (default `/incoming` is clean and current operators don't pass `--file`), but the issue body's threat model — env-var manipulation post-root-compromise, which is exactly what off-site backup exists to survive — is real. `bash -n` + `shellcheck -S error` clean; synthetic test confirms `*[[:cntrl:]]*` catches the injection payload `$'/incoming\\nrm -rf /'` and lets clean paths through.
